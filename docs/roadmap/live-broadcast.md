# Self-hostable live broadcast server

`Status: 📋 planned · Phase 3 · Difficulty: advanced`

Students watch the teacher's board live in a browser, stroke by stroke, through a small relay server that any school can run.

## Goal

Ship `rupok-relay`, a tiny self-hostable server, and a broadcast mode in the
app. The teacher starts a session, students join with a short code or link and
see every page, stroke, Smart Object step and laser pointer in real time, in
the [web viewer](./web-viewer.md). It works for online classes (replacing
screen sharing, at a fraction of the bandwidth) and in rooms where the
projector is poor and students follow on phones.

## User story

- *As a teacher* teaching online, I press **Go live**, paste the link into the
  class chat, and 60 students watch my board in their browsers. My ink is sharp
  at any zoom, unlike a blurry video share, and it works on weak connections.
- *As a teacher*, students who join late see everything I already wrote.
- *As a teacher* at a school with strict IT rules, our IT person runs the relay
  on the school server with one command, and no lesson data leaves the school.
- *As a teacher*, I trust that the relay operator cannot read my lessons
  (end-to-end encryption).

## Scope

- Relay server: rooms, teacher/student roles, fan-out of encrypted messages,
  late-join snapshot, presence count.
- Teacher side: publish Loro updates after each commit, plus ephemeral
  messages (wet strokes, laser, current page, camera).
- Student side: read-only engine that imports updates and follows the teacher's
  page and view; "free look" toggle.
- Broadcast protocol spec (new document).

## Non-goals

- Student write-back (that is [student layers](./student-layers.md) +
  submissions) and live quizzes (see [live-quiz](./live-quiz.md)), which build
  on this.
- Audio/video. Teachers keep their existing call tool for voice.
- Federation between relays, accounts, persistent storage of lessons on the
  relay.

## Design

### Components

```text
teacher app (Board)                relay (rupok-relay)                student (web viewer)
  Engine ── commit ──▶ updates ─▶  room fan-out (WebSocket) ─▶ decrypt ─▶ Engine::import + resync
  Engine ── tick ────▶ ephemeral ▶ (latest-wins per kind)    ─▶ wet layer, laser, page, camera
                                   late join: last snapshot  ─▶ initial load
```

### Relay (new crate `crates/rupok-relay`, binary `rupok-relay`)

- Rust, `tokio` + `axum` WebSockets. Single binary, no database. Config by
  flags/env: listen address, max rooms, max students per room, optional TLS
  (or run behind any reverse proxy).
- Room lifecycle: the teacher `POST /rooms` → `{room, teacher_token}`; students
  connect to `/rooms/<room>/ws` read-only; the teacher connects with the token.
  Rooms die 10 minutes after the teacher disconnects.
- The relay sees only opaque encrypted frames. It keeps the **latest snapshot
  frame** and all **update frames since it** in memory, so late joiners can
  catch up. Memory cap per room (default 64 MiB); when exceeded the teacher
  is asked for a fresh snapshot.
- Ephemeral frames are not stored except the latest of each kind (page,
  camera) for late joiners.
- Licence: AGPL-3.0-or-later like the app. Docker image and a systemd unit in
  `deploy/relay/` (new).

### Protocol (new `spec/broadcast.md`; requires an RFC)

Binary WebSocket frames: `u8 kind | payload`. Payload is
`XChaCha20-Poly1305(key, nonce, body)`. The 32-byte key is generated by the
teacher and travels only in the join link's URL **fragment**
(`https://relay.example/j/ABC123#k=<base64url>`), which browsers never send
to servers.

| kind | body | stored by relay |
|---|---|---|
| `1 snapshot` | Loro snapshot of the lesson (see below) | latest only |
| `2 update` | Loro update bytes since the previous frame | since last snapshot |
| `3 page` | `{page_id}` | latest |
| `4 camera` | `{x, y, zoom}` of the teacher's view | latest |
| `5 wet` | in-progress strokes, ≤ 30 Hz, codec v1 points | no |
| `6 laser` | laser trail points | no |
| `7 presence` | `{students}` count, relay → teacher | no |

Snapshots for viewers may be **shallow** (`ExportMode::ShallowSnapshot` at the
current version) to cut late-join size; viewers then cannot save the lesson,
which is correct (the spec forbids shallow `doc.loro` in saved packages,
`spec/rupok-format.md#docloro`). Package assets and Smart Object bundles are sent
once as `8 blob` frames (content-addressed, so re-sends are skipped).

### Engine and Board API (`crates/rupok-wasm`)

Teacher (new methods):

```rust
impl<S: InkSink> Engine<S> {
    pub fn broadcast_snapshot(&self) -> Vec<u8>;            // shallow snapshot + current page id
    pub fn broadcast_drain(&mut self) -> Option<Vec<u8>>;  // Lesson::export_updates(&last_vv), updates last_vv
    pub fn broadcast_wet(&self) -> Option<Vec<u8>>;        // current wet strokes, encoded with rupok_ink::encode_points
}
```

`broadcast_drain` uses the existing `Lesson::version()` and
`Lesson::export_updates(&VersionVector)` in `crates/rupok-core/src/doc.rs`.
Because every mutation commits, one drain after each frame captures each user
action exactly once.

Student (new methods):

```rust
pub fn apply_remote(&mut self, bytes: &[u8]) -> Result<(), String>;  // Lesson::import + Engine::resync
pub fn set_follow(&mut self, follow: bool);                           // follow teacher page/camera
pub fn set_remote_wet(&mut self, bytes: &[u8]);                       // feeds InkSink::set_wet
```

`Lesson::import` already clears its `top_z` cache; `Engine::resync` already
reconciles scene and renderer after imports.

Board (`crates/rupok-wasm/src/lib.rs`): thin wrappers `broadcast_drain()`,
`apply_remote(bytes)`, `set_follow(bool)`. Networking and crypto stay in
TypeScript (`apps/board/src/live/`, new) using `WebSocket` and WebCrypto
(AES-GCM is fine if XChaCha is unavailable in WebCrypto; decide in the RFC).

### Smart Objects

Step changes and state saves are document commits
(`Lesson::set_object_step`, `set_object_state`), so students' objects follow
the teacher automatically. Student viewers run objects in mode `"present"`
(watching) or `"student"` (interactive, Phase 3 quizzes).

## Implementation tasks

1. **RFC** for `spec/broadcast.md`: frames, encryption, join link format, limits. (advanced)
2. `crates/rupok-relay` skeleton: axum server, room create/join, fan-out, health endpoint, integration test with two WebSocket clients. (intermediate)
3. Relay memory model: latest snapshot + updates, caps, room expiry; load test (`cargo test -p rupok-relay -- --ignored load`). (intermediate)
4. Engine `broadcast_drain` / `apply_remote` with a native test: teacher engine draws 100 strokes, student engine converges to identical `items()`. (intermediate)
5. Wet-stroke and laser ephemeral frames, throttled to 30 Hz. (intermediate)
6. `apps/board/src/live/`: WebSocket client, encryption, reconnect with backoff, "Go live" dialog with QR code and link. (intermediate)
7. Student follow mode: page + camera follow, "free look" toggle, "back to teacher" button. (good-first-issue)
8. Blob frames for assets and Smart Object bundles. (intermediate)
9. Deploy kit: Dockerfile, systemd unit, reverse-proxy snippets, `docs/self-hosting-relay.md`. (good-first-issue)
10. Abuse limits: frame size cap, rate limit per connection, max rooms, token checks. (intermediate)

## Acceptance criteria and tests

- Teacher → student convergence test (native, no network): after random
  edits including undo, page moves and erases, the student's
  `Lesson::items(page)` equals the teacher's for every page.
- Relay integration test: 1 teacher + 200 simulated students in one room on a
  CI runner; every student receives every update frame in order.
- A student joining 2 hours into a class with 20,000 strokes renders the
  current page within the budget below.
- Packet capture on the relay shows no plaintext lesson data.
- Disconnecting the teacher's network for 30 s and reconnecting resumes
  without duplicate or missing strokes.

## Performance budget

- Teacher pen-up → stroke visible on a student screen: p95 ≤ 250 ms over a
  50 ms RTT link; wet ink preview visible ≤ 150 ms.
- Teacher overhead per commit (drain + encrypt + send): ≤ 1 ms p99, so
  `rupok-bench` "stroke commit p99 ≤ 5 ms" still holds with broadcasting on.
- Bandwidth: ≤ 2 KB/s average per student for normal writing (wet frames
  dominate); late-join snapshot for a 2-hour class ≤ 5 MB.
- Relay: 1 room × 200 students on 1 vCPU / 512 MB RAM.

## Open questions

- WebSocket only, or WebTransport later for lossy wet frames?
- Should the relay also be embeddable in the desktop app for LAN-only classes
  (overlaps [lan-send](./lan-send.md))?
- Shallow snapshots drop history; do students ever need replay of a live
  session? (They could download the full lesson after class.)
